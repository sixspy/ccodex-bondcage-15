# 违约出金门闸纪要

- 锁定日：2026-11-22（当日锁死）
- 产品：保证金笼
- 主题：核验违约后解笼口仍亮灯，柜员误走拨付，罚没册空白
- 适用版本：本仓 `backend/` 与 `frontend/` 当前主链路

## 一、事故口径

核验已判「违约」的笼，解笼拨付写口仍可放行；资金按拨付方向离开系统，
罚没册零增。事故夹具：同笼代先有一条「通过」核验，随后出现「违约」结论，
`cages.status` 仍停在「核验通过」。旧解笼口只看状态字符串与一条通过核验，
因此把本该罚没的保证金误拨给收款方。

## 二、正确性口径（二选一，已锁定）

本仓**只启用甲路径**：

> **甲：状态门闸拒写零增。** 解笼写口遇核验违约，直接拒绝；
> 拨付册零增、笼可用额零改、账户冻结零改；并写拒写审计
> `breach_outflow_reject`。

乙路径（误点解笼改道影子罚没意图单，确认后原子晋升罚没册，失败则影子作废）
**明确不启用**，不得与甲路径混用。任何试图以非甲口径写入的请求，一律记为
`gate_deviation`（门闸偏航）并拒写。

## 三、违约态出金规则

1. 违约态**禁止解笼拨付**，只允许罚没方向出金。
2. 判违约以**核验结论**与**笼状态**同源合并为准：当前笼代存在
   `outcome='违约'` 的核验，或笼状态属于 `核验违约 / 部分罚没 / 已罚没`，
   即视为违约态；状态字符串停在通过态也不能放行。
3. 违约笼已有拨付记录的，禁止再罚没；不得一笔钱两边走。
4. 部分罚没后状态为 `部分罚没`，仍可变现尾款继续罚没，直到 `已罚没`。
5. 禁止只把解笼页置灰了事；门闸必须在服务写口生效。

## 四、并发抢写

两人同时对同一违约笼抢写出金，必须先抢笼锁 `cage:{id}`：

- 先到者持锁办理；
- 后到者只留 `contention_log` 争用痕，业务册零写；
- 业务事务回滚不得抹掉争用痕。

## 五、五页同源

解笼页、罚没页、核验页、对账页、审计页的违约态、可出金方向、纪要口径，
必须统一来自 `backend/gate.py` 的同一判定函数，不得各页各写一套。

## 六、验收

- 先见红：违约误拨付失败测、双人同写出金争用失败测；
- 两条红测见红后才允许改解笼/罚没/核验/审计服务与解笼页、罚没页；
- 改完违约只能罚、不能拨；
- 夹具在本机文件库（`data/app.db` 或测试 `tmp_path/*.db`）跑通。
